# 双版本发布核验

本流程用于用户已要求构建/上传的任务；技能本身不新增发布权限。发布动作有明确授权时，校验完成即可继续，不重新请求同一授权。

## 固定交付对象

- 先固定版本、最终源码、两个独立安装包和相应报告。旧版本更新说明取该版本冻结的文档，不复制当前版本的迁移说明冒充旧版。
- 记录源代码版本/工作树状态、安装包Hash、负载manifest和实际运行的测试。源码快照标签若仅含app目录，明确不是完整构建工作区，不宣称可重现整个exe。
- 一并保留本次改动的出戏与数字生命宗旨检查结论，遵循 [角色沉浸感验收](immersion.md)；语言表现的未验收项不得被自动测试通过覆盖。
- 合并 PR 用实际目标分支和基线比较。保护本地其他变更；可在独立检出或发布快照目录工作，禁止为了方便把真实data、临时日志、角色私人资料一并暂存。

## 验证实际产物

1. 从最终 exe 的 `heartecho.payload` 资源解包，逐文件验证manifest；比对关键程序及显式源码清单与测试使用的文件。版本和通用/TB身份都核对。
2. 对两个解包目录及独立发布附件执行仓库 `tools/privacy-audit.mjs`。含压缩包时也审查内部文件；只扫描zip压缩后的字节不等于内容检查。报告仅列相对文件和问题类型，不能回显秘密。保留当前用户自己的升级配置与清空全新分发凭据是不同操作。
3. 用最终负载运行两版实际浏览器流程。安装/路径改变时运行新安装、上一发行版覆盖和自定义目录测试，核实确实执行了用例而非缺少环境变量导致0项。
4. 修改涉及更新器时，拿真实GitHub资产名称测试版型/版本选择、Hash、同意下载/安装、离线提示与安装后更新说明。老安装器识别不了ASCII附件时保留手动覆盖说明，不能宣称自动升级可用。
5. 源码与安装器验收的差异写入报告。真实QQ、真实模型、Docker、干净机和图形安装流程没跑就明确没跑；已知旧失败不得被新的总测试数掩盖。

## 上传与幂等恢复

- 使用新版本标签和草稿release，先上传并核验全部预期资产，再发布为测试/正式类型对应的release。试验版不能因“都绿了”自动变正式版。
- 已存在标签先核验指向；已有资产先比对文件名、大小、`digest`/SHA-256。相同内容跳过；不一致则停止覆盖该资产，保留证据，不使用force覆盖历史标签或公开安装包。
- 网络失败后先查询远端现状再重试，避免重复发布。可列出所有release查找草稿；按tag的查询失败不一定表示没有草稿。最多连续重试三次同一网络动作，再报告已完成部分与阻塞位置；有安全替代传输方式可继续。
- 上传后复查tag、release状态及全部资产Hash；下载名和链接必须来自远端实际返回。只有草稿、只有本地文件或只有tag都不能说“已发布”。
- 中文产品名不保证成为同名GitHub资产，实际下载通常使用 `HeartEcho-版本-Setup.exe` 与 `HeartEcho-TB-版本-Setup.exe`；校验文件使用远端相同名称。

## 交付记录

保留已验证的release URL、tag SHA、资产名称/大小/Hash、版型、测试和隐私审查结果。向用户说明覆盖安装无需重复导入、原文/摘要补整理的范围以及真实验收限制。旧不安全版本仅保留说明，不为了“完整历史”重新分发泄露包。
